Lyrion Anywhere **0.6.4** is a maintenance release: a gateway fix for the last bytes before a stream failure, the three security patches to the Rust TLS and hashing crates published on 23 October, the web app rebuilt on SvelteKit 3, `cloudflared` 2026.10.3 for the built-in tunnel, and the dependency updates of the past week. Everything else is as in [0.6.3](https://github.com/JameZUK/lyrion-anywhere/releases/tag/v0.6.3). Android [1.15.8](https://github.com/JameZUK/lyrion-anywhere/releases/tag/android-v1.15.8) is released alongside with the same dependency refresh. Update from *Settings › Plugins* in LMS; LMS restarts to load it. The web app updates itself in the background and offers a reload when it is ready.

## Gateway

- **The bytes before a stream failure reach the client.** When a response body fails, hyper drops whatever output it has not yet written to the socket. If the relay handed over a chunk and a failure in the same turn (an encoder that wrote its last bytes and then exited with an error), the chunk was lost and the client saw the error and none of the bytes. The relay now hands control back once before it reports an error, so what it has already sent is written out first. A player would have resumed from `?offset=` and got the bytes from the replay window, so nothing was heard wrong; the response just wasn't what the gateway had sent. Found through a test that failed on a loaded CI runner; it has a regression test now.
- **`cloudflared` 2026.10.3.** The built-in Cloudflare Tunnel installs this release (pinned, SHA-256 checked), moved from 2026.10.1. An existing tunnel install keeps running on the old one until you press *Update* on the plugin's settings page, which offers it.
- **A tunnel install is no longer refused by a stream starting at the same instant.** After downloading `cloudflared`, the gateway runs it once to read its version. If an encoder for a stream was being started in that same instant, the new file could still be held open for writing by that child for a moment, the run failed with "text file busy", and the install ended with "The downloaded cloudflared does not run on this system". The check now waits for the writer to go (up to half a second) before giving up. Seen on a loaded CI runner; it has a regression test.

## Security

Three advisories against crates the gateway's outbound TLS and its password hashing use, all fixed by patch updates and shipped here:

- `rustls-webpki` 0.103.16 (RUSTSEC-2026-0382): certificate verification could accept a distrusted intermediate.
- `webpki-root-certs` 1.0.11 (RUSTSEC-2026-0383): the bundled root store trusted a distrusted emSign root.
- `ctutils` 0.4.5 (RUSTSEC-2026-0385): comparisons under the hash and password-hash crates were not constant-time.

`npm audit` on the web app now reports no vulnerabilities (the three low advisories against the `cookie` package under SvelteKit 2 are gone with the move below).

## Web app

- **Rebuilt on SvelteKit 3.1 and adapter-static 4.** The app itself is unchanged: one static page with hash routes and relative paths, the same worker and WebAssembly core, and the gateway's strict Content Security Policy still holds. The service worker is now registered as a module worker, as SvelteKit 3 does; it behaves the same.

## Build and dependencies

- The first release built on node 26 (the web app's build stage). The gateway is built as before.
- Rust: tokio 1.53.3, serde_json 1.0.154, rustls-native-certs 0.8.5, sha2 0.11.1, getrandom 0.4. Web: svelte 5.57.2, vite 8.3.4.
- Android builds are now published as full GitHub releases (never marked *Latest*, which stays the plugin's for the repository URL above).
- Three timing-sensitive tests that failed on busy CI runners are reliable now; one of them found the gateway fix above.
